## Context

Investra handles diverse media types: startup pitch decks (large PDFs), user profile avatars (images), KYC verification files (confidential PDFs/images), and pitch presentation media. Directly handling multi-megabyte binary uploads through the NestJS backend creates severe memory spikes, ties up Node.js event loops, and causes excessive server bandwidth costs. 

See `proposal.md` for motivation and `specs/media-storage/spec.md` for behavioral requirements.

## Goals / Non-Goals

**Goals:**
- Provide zero-load binary uploads to NestJS by utilizing Cloudflare R2 presigned PUT URLs directly from the browser.
- Segregate storage across two physical R2 buckets: a **Public Bucket** for marketplace media and a **Private Bucket** for sensitive KYC/financial media.
- Store object keys in the database and derive public URLs dynamically (`R2_PUBLIC_URL + "/" + key`), enabling seamless domain/CDN migrations without database schema alterations.
- Implement a robust 5-state lifecycle (`PENDING_UPLOAD` → `UPLOADED` → `ACTIVE` → `DELETE_PENDING` → `DELETED`) with two-phase commit and transactional safe media replacement.
- Deliver a free-hosting-compatible cleanup strategy for orphaned files that works reliably on sleep-prone platforms (such as Render Free).
- Support direct short videos (<100MB) with an optional YouTube/Vimeo embed link fallback for high-definition startup presentations.
- Deliver modular, reusable Next.js upload components with drag-and-drop, upload progress (via `XMLHttpRequest`), cancellation, and deletion handling.

**Non-Goals:**
- In-depth content virus/malware inspection and executable sandbox analysis (outside initial scope; reliance is placed on strict MIME whitelisting, extension filtering, signature enforcement, and size caps).
- Real-time video transcoding (HLS/DASH) on backend compute; startups needing adaptive streaming will use YouTube/Vimeo links.

## Decisions

### Decision 1: Two Separate Cloudflare R2 Buckets (Public vs. Private)
- **Choice:** Maintain two dedicated buckets configured via environment variables:
  - `R2_PUBLIC_BUCKET_NAME`: Contains public assets (`AVATAR`, `CAMPAIGN_COVER`, `CAMPAIGN_GALLERY`, public `VIDEO`). Configured with public read access (using Cloudflare's free `r2.dev` development domain or custom CDN domain `R2_PUBLIC_URL`).
  - `R2_PRIVATE_BUCKET_NAME`: Contains confidential assets (`KYC_DOCUMENT`, `CONFIDENTIAL_PITCH_DECK`, `FINANCIAL_REPORT`). Completely closed to public HTTP access. Objects are accessed only via temporary 15-minute Presigned GET URLs generated by NestJS after authenticating and authorizing the request.
- **Rationale:** Strict physical isolation prevents catastrophic configuration leaks (e.g., misconfigured bucket permissions exposing investor passports or founder NIDs).

### Decision 2: Environment Configuration Architecture
- **Choice:** Standardize on explicit multi-bucket environment variables:
  ```env
  R2_ACCOUNT_ID="your-cloudflare-account-id"
  R2_ACCESS_KEY_ID="your-r2-access-key-id"
  R2_SECRET_ACCESS_KEY="your-r2-secret-access-key"
  R2_ENDPOINT="https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com"
  R2_PUBLIC_BUCKET_NAME="investra-media-public"
  R2_PRIVATE_BUCKET_NAME="investra-media-private"
  R2_PUBLIC_URL="https://pub-xxxx.r2.dev" # Or custom domain e.g. https://cdn.investra.com
  ```
- **Rationale:** Separating `R2_PUBLIC_BUCKET_NAME` and `R2_PRIVATE_BUCKET_NAME` prevents code from inadvertently using the wrong bucket. `R2_PUBLIC_URL` allows instant migration from `r2.dev` to a custom domain without running database migrations.

### Decision 4: 5-State Media Lifecycle and Safe Replacement
```
[Client presign request] 
       │
       ▼
 PENDING_UPLOAD  ──(Browser direct PUT)──►  R2 HeadObject Check
       │                                            │
       │                                            ▼
       │                                        UPLOADED
       │                                            │
       ▼ (Attach to Entity Commit)                  ▼ (User clicks Remove)
     ACTIVE                                    DELETE_PENDING
       │                                            │
       ▼ (Replaced by new media)                    ▼ (DeleteObject in R2)
 DELETE_PENDING ──(DeleteObject in R2)──►        DELETED
```

#### Safe Media Replacement Algorithm:
1. User uploads new image: creates `MediaFile` record with status `UPLOADED`. Existing image remains `ACTIVE`.
2. User submits Profile / Campaign form:
   - Begin database transaction.
   - Update parent entity relation: `avatarMediaId = newMedia.id`.
   - Update new media: `status = ACTIVE, activatedAt = now()`.
   - Update old media: `status = DELETE_PENDING`.
   - Commit transaction.
3. Post-commit action:
   - Call R2 `DeleteObject` for the old media key.
   - On success, update old media: `status = DELETED, deletedAt = now()`.
   - On R2 failure, old media stays in `DELETE_PENDING` for cleanup retry.
4. If database transaction fails:
   - Transaction rolls back. Old media remains `ACTIVE`. New media remains `UPLOADED`. Zero data loss.

### Decision 5: Prisma Schema Architecture
```prisma
enum MediaCategory {
  AVATAR
  CAMPAIGN_COVER
  CAMPAIGN_GALLERY
  PITCH_DECK
  CONFIDENTIAL_PITCH_DECK
  FINANCIAL_REPORT
  KYC_DOCUMENT
  VIDEO
}

enum MediaAccessType {
  PUBLIC
  PRIVATE
}

enum MediaUploadStatus {
  PENDING_UPLOAD
  UPLOADED
  ACTIVE
  DELETE_PENDING
  DELETED
}

model MediaFile {
  id           String            @id @default(uuid())
  key          String            @unique
  bucket       String
  originalName String
  mimeType     String
  sizeBytes    BigInt
  accessType   MediaAccessType
  category     MediaCategory
  status       MediaUploadStatus @default(PENDING_UPLOAD)
  uploadedById String
  uploadedBy   User              @relation("UploadedMedia", fields: [uploadedById], references: [id], onDelete: Cascade)
  activatedAt  DateTime?
  deletedAt    DateTime?
  createdAt    DateTime          @default(now())
  updatedAt    DateTime          @updatedAt

  // Inverse relations for entities
  userAvatar   User?             @relation("UserAvatar")
  campaignCover Campaign?        @relation("CampaignCover")
  campaignPitchDeck Campaign?    @relation("CampaignPitchDeck")

  @@index([uploadedById])
  @@index([category, status])
  @@index([status, createdAt])
}
```

### Decision 6: Free-Hosting-Compatible Cleanup Strategy (Render Free Safe)
- **Problem:** Render Free tier services spin down and sleep after periods of inactivity. An in-process `setInterval` or `node-cron` will miss execution windows.
- **Solution:**
  1. **Idempotent Maintenance Endpoint:** Expose `POST /api/v1/media/internal/cleanup` protected by a shared secret header (`X-CLEANUP-SECRET`).
  2. **External Trigger:** Can be invoked periodically by free web-cron services (such as cron-job.org, GitHub Actions scheduled workflow, or Cloudflare Worker Cron Trigger).
  3. **Cleanup Logic:**
     - Query `MediaFile` records where `status IN ('PENDING_UPLOAD', 'UPLOADED')` and `createdAt < NOW() - 24 hours`.
     - Query `MediaFile` records where `status = 'DELETE_PENDING'`.
     - For each record, execute `DeleteObject` in R2 and update status to `DELETED, deletedAt = NOW()`.
  4. **Optional R2 Bucket Lifecycle Rule:** Configure R2 object lifecycle rule to expire any incomplete multipart uploads after 7 days.

### Decision 7: R2 Object Key Pattern & CORS Setup
- **Key Pattern:**
  - `users/{userId}/avatar/{uuid}.{ext}`
  - `campaigns/{campaignId}/cover/{uuid}.{ext}`
  - `campaigns/{campaignId}/gallery/{uuid}.{ext}`
  - `kyc/{userId}/{uuid}.{ext}`
- **R2 Bucket CORS Configuration:**
  ```json
  [
    {
      "AllowedOrigins": [
        "http://localhost:3000",
        "https://investra.com",
        "https://*.investra.com"
      ],
      "AllowedMethods": ["GET", "PUT", "HEAD"],
      "AllowedHeaders": ["*"],
      "ExposeHeaders": ["ETag"],
      "MaxAgeSeconds": 3600
    }
  ]
  ```

### Decision 8: Video Handling Architecture
- **Direct Video:** If file is < 100MB and MIME is `video/mp4` or `video/webm`, upload directly to Public R2 under `campaigns/{campaignId}/video/{uuid}.mp4`.
- **External Video Fallback:** If founder provides YouTube or Vimeo link, campaign model stores `videoProvider: 'YOUTUBE' | 'VIMEO'` and `videoExternalUrl`. Server validates URL regex:
  - YouTube: `^(https?:\/\/)?(www\.)?(youtube\.com\/watch\?v=|youtu\.be\/)[a-zA-Z0-9_-]+`
  - Vimeo: `^(https?:\/\/)?(www\.)?vimeo\.com\/[0-9]+`
- External videos never generate `MediaFile` or R2 objects.

## Risks / Trade-offs

- **[Risk] Render Free Sleep prevents cleanup** → **Mitigation:** Documented external cron trigger (`POST /api/v1/media/internal/cleanup`) callable from free external cron or GitHub Actions.
- **[Risk] Malicious file disguised as harmless format** → **Mitigation:** Backend validates declared MIME, whitelisted extensions, enforces `Content-Type` matching in the S3 PUT signature, and verifies byte size on `HeadObject`. Deep sandbox inspection is acknowledged as outside the initial scope.
- **[Risk] R2 DeleteObject fails during media replacement** → **Mitigation:** Transactional two-phase commit marks the asset as `DELETE_PENDING` so it is safely retried by the cleanup job rather than leaving orphaned objects.
